## 一、项目架构与数据库（4 题）

### 1.【基础】你的项目用了多数据源，MySQL 和 ClickHouse 分别承担什么角色？为什么这么分？

**参考要点**
- MySQL 存业务主数据：渠道、渠道号、字段维护、数据等级标注、校验规则、实时验证数据（`tb_real_time_data_verification`）。
- ClickHouse 存埋点行为轨迹大数据（`tb_easydata_user_trackinfo_complete_*`），量大、只读分析、按天分区。
- 划分依据：OLTP 与 OLAP 分离。行为日志单日上亿、只做聚合统计，放 MySQL 会拖垮业务库；ClickHouse 列式存储 + 分区裁剪，GROUP BY 聚合性能碾压 MySQL。
- 实现：Spring 的 `@DataSource` 注解 + 自定义 `DynamicDataSource`（继承 AbstractRoutingDataSource），通过 `DataSourceType` 枚举切换，Druid 连接池统一管理。
- 注意点：切换数据源要 try/finally 清理 ThreadLocal，防止线程池复用线程时串库（项目里 `DynamicDataSourceContextHolder.clearDataSourceType()`）。

### 2.【深挖】ClickHouse 和 MySQL 在 SQL 语法上有哪些差异？你的项目踩过哪些坑？

**参考要点**
- 引擎：ClickHouse 是 MergeTree 家族（按分区 + 排序键存储），MySQL 是 InnoDB（B+树）。
- 语法差异：ClickHouse 支持 `PREWHERE`、`FULL OUTER JOIN`、`FROM_UNIXTIME`、`toDecimal64` 等；MySQL 不支持。
- 分页：MySQL `LIMIT/OFFSET` 直接可用；ClickHouse 深度分页也支持 LIMIT，但数据量大时不建议。
- **项目实坑 1（PageHelper 双 ORDER BY）**：PageHelper 的 `startPage(pageNum,pageSize,orderBy)` 三参数重载只会在 SQL 末尾再拼一个 `order by`，如果 Mapper 里已手写 ORDER BY，就会生成双 ORDER BY 语法错误。所以行为轨迹查询绕开了 PageHelper，改走全量查询 + Caffeine 缓存 + `List.subList` 内存分页。
- **项目实坑 2（PageHelper 无 ClickHouse 方言）**：`helperDialect=mysql` 写死，对 ClickHouse 做 COUNT 重写时套 MySQL 规则，遇到 PREWHERE 会解析失败。
- 时间函数差异：项目里用 `intDiv(toInt64OrZero(ifNull(wt_dcsdat,'0')),1000)` 把毫秒时间戳转秒，再 `FROM_UNIXTIME` 格式化——这套写法 MySQL 没有。

### 3.【深挖】自定义规则统计的 SQL 为什么要用 CTE（WITH ... AS）一层层套？讲讲思路。

**参考要点**
- 业务：按渠道/事件/营销码/页面链接多条件筛选，再按指定字段分组统计数量、占比，还支持"统计期 vs 对比期"变化率。
- CTE 分层（t1→t2→t3→t4）：
  - `t1`：基础筛选（statis_date、数据源、事件类型、营销码、页面链接）
  - `t2`：时间过滤（不同数据源时间字段不同，用 CASE WHEN 统一口径）
  - `t3`：GROUP BY 分组计数，`ORDER BY statistics_num DESC LIMIT 100`
  - `t4`：算占比 `statistics_num * 100 / SUM(statistics_num)`
- 好处：可读性高、每层职责单一、便于调试（可以单独跑某一层验证）。
- 对比期版本：t4/t7 分别算统计期和对比期，最后 `FULL OUTER JOIN` 用 `COALESCE` 补齐空值，再算绝对变化量和变化率。
- 亮点：`checkField` 是动态传入的（`${checkField}`），同一套 SQL 支持任意维度分组。

### 4.【基础】数据等级标注的"冲突检测 + 强制覆盖"怎么设计的？

**参考要点**
- 表结构：`tb_data_level_label(channel_id, event_code, data_level)`，渠道×事件唯一。
- 批量新增是笛卡尔积：渠道集合 × 事件集合 组合后插入。
- 冲突检测：已存在且等级相同 → 静默更新；已存在且等级不同 → 返回 `needConfirm=true` + 冲突列表（前端弹窗）。
- 强制覆盖：弹窗确认后前端带 `forceUpdate=true` 重发，后端走覆盖逻辑。
- 前端交互：`doAdd()` 收到 `needConfirm` 后用 `$modal.confirm` 二次确认，确认后自动把 `forceUpdate` 置 true 再提交。

## 二、长链接与实时推送（3 题）

### 5.【基础】你说你做了"模拟长连接"，为什么用 HTTP 轮询而不是 WebSocket？后来为什么又升级成 WebSocket？

**参考要点**
- 第一版轮询的原因（代码注释里明确写了）：简单可靠、无需维护长连接、服务端资源占用小、3 秒延迟对日志查看场景可接受；且当时 WebSocket 模块未接入业务。
- 轮询实现：前端每 3 秒调 `GET /manage/behaviorLog/incremental?userMobile=xxx&queryTime=xxx`，后端查 `event_time > queryTime` 的增量，返回 `queryEndTime` 作为下次基准。
- 轮询痛点：实时性差（固定 3s 延迟）、无新数据时也发无效 HTTP 请求、占用 Tomcat 线程。
- 升级 WebSocket：项目里已有 `icm-websocket` 模块（连接池、消息实体、心跳协议），改造为 `@ServerEndpoint("/ws/{scene}/{userMobile}")`，数据生成器写入后由服务端**主动推送**，实现毫秒级实时。
- **面试加分点**：保留轮询作为降级方案，WebSocket 不可用时自动回退，功能不中断。

### 6.【深挖】WebSocket 的增量推送，你怎么保证前端拿到的数据不重不漏？

**参考要点**
- 后端推送时机：数据生成器在**写入成功后**立即调 `pushBehavior(scene, mobile, content, data)` 推送，一次插入一条推送一次，天然不重不漏（和"轮询按时间查"不同，不是拉取而是推）。
- 手机号脱敏：前端展示 `138****8000`，脱敏在 VO 层做。
- 心跳保活：客户端每 30s 发 `type=3`，服务端回 `pong`；连接级 `ConcurrentHashMap<sessionKey, Session>` 管理订阅。
- 断线重连：`onclose` 触发指数退避重连（1s→2s→4s→…→30s 封顶），重连成功后从最新时间点继续。
- 防重机制：连接 key 用 `scene::userMobile`，同一 key 新连接会**关掉旧连接**（`old.close()`），避免重复订阅。

### 7.【场景】如果用户断网 5 分钟再恢复，WebSocket 重连后中间的数据丢了怎么办？

**参考要点（开放设计）**
- WebSocket 只做"实时增量"，不做可靠传输。断线期间的数据通过 HTTP 接口兜底：
  - 前端记录断线时间 `disconnectTime`，重连成功后先调一次 `GET /manage/behaviorLog/incremental?queryTime=disconnectTime` 拉取断线期间的增量，再切回 WebSocket 实时流。
- 即"WebSocket 推实时 + HTTP 拉补偿"的双通道设计。
- 更重的方案：前端本地存 lastSeq/时间游标 + 后端消息带序号（seq），重连后按序号补齐。项目当前用第一种（简单够用）。

## 三、缓存与 Redis（2 题）

### 8.【基础】用户行为轨迹查询为什么用"Redis + Caffeine 多级缓存"？降级逻辑是什么？

**参考要点**
- 场景：ClickHouse 查询慢 + 前端频繁翻页，行为轨迹数据同一手机号短期内变化不大，适合缓存。
- 多级缓存：L1 Redis（分布式，多实例共享）→ L2 Caffeine（本地，快）→ DB/ClickHouse。
- 降级逻辑：`@Autowired(required=false) RedisTemplate` 注入失败或 Redis 不可用时，`redisEnabled && redisTemplate != null` 为 false，自动降级为仅 Caffeine 本地缓存（最大 1000 条、20 分钟过期）——**不会因为 Redis 挂了导致功能不可用**。
- 缓存 key：`user:behavior:track:{phone}:{query条件}`，TTL 5 分钟。
- 缓存一致性：简单场景用过期时间，不主动淘汰；面试可延伸：更新/删除时主动清缓存、双删、延迟双删。

### 9.【深挖】为什么项目里 `RedisTemplate<String, Object>` 注入进来是 null，验证码却能正常用 Redis？

**参考要点**
- 项目 `RedisConfig` 只定义了 `RedisTemplate<Object,Object>` 和 `RedisTemplate<String,String>` 两个 Bean。
- 业务 Service 里注入的是 `RedisTemplate<String, Object>`，**没有这个泛型类型的 Bean**，`required=false` 导致注入 null，代码判断后走 Caffeine 降级。
- 验证码（CaptchaController）用的是另一个模板，所以 Redis 本身是通的。
- 启发：`@Autowired(required=false)` 的优雅降级 + 依赖注入的类型/泛型要匹配。面试可反过来说：如果改成 `RedisTemplate<Object,Object>` 注入就能命中 Bean。

## 四、并发与数据生成器（2 题）

### 10.【基础】数据生成器（模拟埋点上报）怎么保证线程安全和优雅停止？

**参考要点**
- 线程安全：
  - `ReentrantLock` 控制启动/停止互斥，防止并发 start/stop 冲突；
  - `AtomicLong` 做自增计数（id、insertCount、errorCount），无锁高性能；
  - `volatile boolean running` 保证多线程可见性。
- 定时执行：`ScheduledExecutorService.scheduleAtFixedRate` 每秒/每毫秒批量插入，daemon 线程。
- 优雅停止：`CountDownLatch` 等待当前批次结束；`@PreDestroy` 在应用关闭时释放线程池；停止时清 running 标志、shutdown 调度器。
- 5 分钟自动停止：用 `scheduler.schedule(stop, 5, MINUTES)`，不用人工干预。

### 11.【场景】如果你的数据生成器要支撑每秒 1000 条写入，现在的单线程定时任务扛得住吗？怎么优化？

**参考要点（开放设计）**
- 现在 `scheduleAtFixedRate` 单线程，一次插一条/小批量，TPS 上限低。
- 优化方向：
  1. **批量插入**：攒批（如每 100ms 攒 500 条）用 MyBatis 批量 insert，减少网络/事务开销；
  2. **多线程分片**：固定线程池按手机号 hash 分片并行写；
  3. **异步解耦**：生成器只往 MQ（RabbitMQ）发事件，消费者批量落库（项目 Docker 里有 rabbitmq 容器）；
  4. **写 ClickHouse 用批量 buffer**：`INSERT ... VALUES (...),(...),...` 一次多条，ClickHouse 批量写入吞吐远高于单条。

## 五、Spring Boot 与工程实践（3 题）

### 12.【基础】RuoYi 的 token 认证流程讲一下？JWT 和 Session 的区别？

**参考要点**
- 流程：登录成功 → 生成 JWT（含 login_user_key）→ 存 Redis（`login_tokens:{uuid}` 存 LoginUser）→ 返回 token 给前端。
- 前端每次请求带 `Authorization: Bearer {token}`。
- `JwtAuthenticationTokenFilter` 每次请求解析 token → 查 Redis 拿 LoginUser → 放入 SecurityContext，实现无状态认证。
- JWT vs Session：
  - Session 是服务端存储，集群要共享（粘性会话/Redis 共享 session），天然有状态；
  - JWT 本身携带信息、无状态、适合分布式，但存在服务端"无法主动失效"的问题（所以要配合 Redis 黑名单/存 session 实现登出）。
- 本项目：JWT 只存一个随机 key，真正的用户信息放 Redis——**JWT 做凭证，Redis 做状态**，兼顾无状态和可控失效。

### 13.【深挖】Redis 里缓存了登录用户信息，如果用户被禁用/改角色，怎么让它立即生效？

**参考要点**
- 若依的做法：登录后 Redis 里 `login_tokens:{uuid}` 存 LoginUser（含权限）。
- 立即生效方案：修改用户/角色/权限时，**删除该用户对应的 Redis token**（`redisCache.deleteObject("login_tokens:" + tokenId)`），下次请求 JwtAuthenticationTokenFilter 查不到缓存即认为未登录。
- 或者：改权限时不删 token，而是让 LoginUser 每次从 DB 重查权限（牺牲一点性能换实时性）。
- 延伸：这就是缓存一致性问题——主动失效（删缓存）优于等待过期。

### 14.【基础】你在 Mac 上跑这个项目遇到过什么环境问题？怎么解决的？（讲 2-3 个）

**参考要点（真实经历，面试可复述）**
1. **logback 日志路径写死 `/home/ruoyi/logs`**：Linux 路径在 Mac 上创建不了目录，启动直接失败。改成本地可写路径。
2. **沙箱注入 `SERVER__PORT=0` 环境变量**：Spring Boot 把它绑定到 `server.port`，导致随机端口、连不上。启动时显式 `SERVER_PORT=8080` 覆盖。
3. **ClickHouse 缺 httpclient5 依赖**：ClickHouse JDBC 走 HTTP 协议需要 Apache HttpClient5，但 SpringBoot 2.5 BOM 把版本锁成 5.0.4（缺 `ConnectionConfig` 类），运行时抛 `ClassNotFoundException`。在父 pom dependencyManagement 覆盖为 5.3.1。
4. **Redis 无密码但配置写了 123456**：连接认证失败，应用降级为本地缓存；改成空密码配置。
5. **ClickHouse 容器没有 admin 用户**：应用配置用 admin/123456，实际容器只有 default 用户，改成 default/123456。

## 六、高频八股抽查（4 题）

### 15.【基础】`@Transactional` 失效的场景有哪些？

**参考要点**
1. 方法不是 public（Spring AOP 基于代理，private/protected 不代理）；
2. 同类内部调用（this.method() 不走代理）；
3. 异常被 catch 吞掉（默认只对 RuntimeException/Error 回滚，checked 异常不回滚，除非 rollbackFor）；
4. 类没被 Spring 管理（没加 @Service/@Component）；
5. 多线程调用（新线程不共享事务）；
6. 数据库引擎不支持事务（MyISAM）。

### 16.【基础】MySQL 索引为什么用 B+ 树？和 B 树、Hash 的区别？

**参考要点**
- B+ 树：非叶子节点只存 key（更矮，减少 IO）、叶子节点链表有序（范围查询友好）、数据全在叶子。
- B 树：每个节点都存数据，树更高，范围查询要中序遍历。
- Hash：等值查询 O(1) 最快，但**不支持范围查询/排序/最左前缀**，所以 InnoDB 默认 B+ 树；自适应 Hash 索引只做等值加速。
- 引申：联合索引最左前缀、覆盖索引、回表、explain 的 type/ref 判断。

### 17.【基础】Redis 持久化 RDB 和 AOF 的区别？项目里一般怎么选？

**参考要点**
- RDB：全量快照，恢复快、文件小，但可能丢最后一次快照后的数据（fork 子进程，对主进程影响小）。
- AOF：追加写命令日志，数据更安全（可配 everysec），但文件大、恢复慢；AOF rewrite 会压缩。
- 混用：Redis 4.0+ 支持混合持久化（RDB 打底 + AOF 增量）。
- 项目场景：缓存为主可容忍丢失 → RDB；对账/关键数据 → AOF everysec 或混合。

### 18.【基础】接口幂等怎么设计？（你的日志采集接口怎么防重复上报？）

**参考要点**
- 幂等：同一请求执行多次结果一致。
- 常见方案：
  1. 唯一索引（如手机号+事件+时间戳唯一，重复插入报错/忽略）；
  2. 前端生成 requestId，后端 Redis setnx 判重（防重表）；
  3. 乐观锁版本号、状态机校验。
- 本项目埋点采集：`tb_real_time_data_verification` 可加唯一键，或用幂等表 `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE`。
- 面试延伸：分布式场景用 Redis setnx + 过期时间，或数据库唯一约束兜底（双保险）。

## 七、追问杀手锏（2 题）

### 19.【场景】如果 ClickHouse 挂了，你的行为轨迹查询怎么保证平台不挂？

**参考要点**
- 现有兜底：Redis/Caffeine 缓存——命中缓存时根本不查 ClickHouse。
- 加强方案：
  1. 数据源故障自动降级：Druid 连接失败时 catch 异常，返回友好提示 + 降级到离线报表数据；
  2. 熔断：引入 Resilience4j/Sentinel 对 ClickHouse 查询做熔断（失败率阈值触发），避免雪崩；
  3. 双写：行为数据同时写 ClickHouse 和 MySQL 冷备表（或 MQ 重放）；
  4. 只读降级开关：`@Value("${query.clickhouse.enabled:true}")` 配置开关，故障时一键切 MySQL 兜底。
- 项目现状：轨迹查询已做到"查不到就走缓存/空结果"，不会抛异常拖垮主流程。

### 20.【场景】你的系统要给运营做"按渠道看用户行为分布"的报表，数据量上亿，怎么设计查询？

**参考要点**
- 存储：ClickHouse，按 `statis_date` 分区 + `(daytime, wt_mobile)` 排序键，分区裁剪过滤。
- 预聚合：报表维度固定（渠道/事件/页面），可以建物化视图（AggregatingMergeTree）或离线 T+1 预聚合表，查询秒级返回。
- 查询优化：只查需要的列（列式存储优势）、`PREWHERE` 过滤、`LIMIT` 限制。
- 缓存：报表结果 Redis 缓存（按日期+维度 key），凌晨任务刷新。
- 大促场景：冷热分层，历史数据归档到低成本存储。
